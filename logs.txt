# Навык: Турагент (Tour Agent)

## Описание
Специализированный навык подбора путешествий: перелёт/проезд, отели, трансферы,
сравнение вариантов и формирование итогового предложения со ссылкой на оформление.
Работает через MCP-сервер Туту, вызываемый **единым инструментом** `tutu_call`.

## Когда использовать
- «Подбери тур в [город/страну]»
- «Найди билеты из Москвы в Сочи на завтра»
- «Посоветуй отель на побережье»
- «Сравни цены на самолёт и поезд», «как добраться из … в …»

## Как вызывать инструменты Туту (ВАЖНО)
Все инструменты Туту вызываются через прокси `tutu_call(tool, args_json)`:
- `tool` — имя инструмента из «Каталога инструментов Туту» в системном промпте;
- `args_json` — аргументы **строкой JSON**.

### ⚠️ Точные имена полей (сервер жёстко валидирует — `extra_forbidden`)
Бери имена полей **только** из колонки «Параметры» каталога системного промпта.
Частые ошибки (из-за них были сбои):
- поля отправления/прибытия — **`origin` / `destination`** (НЕ `from_city`/`to_city`);
- число путешественников у авиа — это **`adults`** (поля `passengers` у
  `search_avia` НЕТ); у `search_rail` — сверяйся с каталогом;
- **`departure_date` обязателен** для всех поисковых инструментов — сначала
  уточни дату у пользователя, только потом вызывай поиск;
- фильтра «прибытие до HH:MM» на сервере НЕТ — получи офферы и **отфильтруй по
  времени сам** в тексте ответа;
- не передавай `return_date` в `search_multitransport`.

Если `tutu_call` вернул «нет полей …» или «не хватает обязательных полей …» —
исправь `args_json` строго по подсказке и повтори. Это клиентская проверка ДО
обращения к серверу, она не тратит серверный вызов и токены на ответ сервера.

### Примеры (правильные имена полей)
```
tutu_call(tool="search_avia",
          args_json='{"origin":"Москва","destination":"Сочи","departure_date":"2026-08-15","adults":2}')

tutu_call(tool="search_rail",
          args_json='{"origin":"Москва","destination":"Сочи","departure_date":"2026-08-15","passengers":2}')

tutu_call(tool="search_multitransport",
          args_json='{"origin":"Москва","destination":"Сочи","departure_date":"2026-08-15","adults":2}')

tutu_call(tool="search_hotels",
          args_json='{"city_name":"Сочи","check_in":"2026-08-15","check_out":"2026-08-22","guests":2}')
```

# Etrain playbook — commuter / suburban trains (электрички)
(`search_etrain` -> `create_checkout_link`)

## Station disambiguation (mandatory)
A city often has several commuter stations far apart — СПб (Московский /
Ладожский / Балтийский …), Москва (the radial вокзалы). The departure /
arrival point is in `legs[].segments[].from|to` as a self-describing
string `"City — Station (code)"` (e.g. `"Санкт-Петербург — Московский
вокзал (2004003)"`). Always name the concrete station when comparing
offers — never present two electrichkas that leave the same city from
different stations as if they share an origin, and never make the user
read the station out of the checkout URL.

## Place resolution (`meta.from` / `meta.to`)
Each side echoes the place that was searched: `name`, `geo_id`, `region`.
`match` + `query` are present only when the resolved name differs from
the wording you sent — `lead` (Tutu's own ranking read a short form or
typo: «Питер», «Масква»), `qualified` (the trailing words acted as a
region filter: «Красная Поляна, Краснодарский край»), `prefix` (the name
was completed). Say which place came back and keep going; a synonym is
never a reason to stop and confirm. `also_named[]` lists same-name places
that lost to a better-connected one — mention them with a one-line
invitation to correct, never as a blocking question.
Two wordings are refused with an error instead of being searched as some
other city, and the error text is the instruction:
- `could not resolve … N places share this name and none is better
  connected …` — an exact-name tie. The candidates are listed with their
  regions, and the text may add what Tutu's hotel index lists under this
  name. Ask the user which one is meant, or resend as '<name>, <область
  или район>' (name first, no parentheses). Do not pick one yourself.
- `could not resolve … no place with this name in Tutu's transport index
  …` — the fuzzy suggestions were unrelated places and were NOT searched.
  If the text says Tutu's hotel index lists it, hotels there ARE
  searchable — say so and offer `search_hotels`; never report it as
  «транспорта нет». Otherwise check the spelling with the user.
`… has no <id> in Tutu's index` means the place resolved but this
transport has no node there — ask for a place that has one; when the text
names the city Tutu's avia index answered with, offer it and search it
only after the user agrees. `Tutu's geo index did not answer` is a
transient upstream error: retry the call.

# Навык: Авиаперелёты (Avia Agent)

## Описание
Специализированный навык поиска и бронирования авиабилетов: прямые рейсы, пересадки, сравнение тарифов.
Работает через MCP-сервер Туту, вызываемый **единым инструментом** `tutu_call`.

## Когда использовать
- «Найди билеты на самолёт из Москвы в Сочи»
- «Прямой рейс без пересадок»
- «Сравни бизнес/эконом класс»
- «Авиабилеты с багажом и без»

## Как вызывать инструменты Туту (ВАЖНО)
Все инструменты Туту вызываются через прокси `tutu_call(tool, args_json)`:
- `tool` — имя инструмента из «Каталога инструментов Туту» в системном промпте;
- `args_json` — аргументы **строкой JSON**.

### ⚠️ Точные имена полей для АВИА
- Поля отправления/прибытия — **`origin` / `destination`** (НЕ `from_city`/`to_city`);
- Число взрослых — **`adults`** (НЕ `passengers` у `search_avia`);
- **`departure_date` обязателен** — сначала уточни дату у пользователя;
- Коды IATA: SVO (Шереметьево), DME (Домодедово), VKO (Внуково), AER (Сочи), LED (Пулково).

### Примеры вызовов
```
tutu_call(tool="search_avia",
          args_json='{"origin":"Москва","destination":"Сочи","departure_date":"2026-08-15","adults":2}')

tutu_call(tool="get_offer_details",
          args_json='{"offer_id":"12345","view":"compact"}')

tutu_call(tool="create_checkout_link",
          args_json='{"offer_id":"12345"}')
```

## Рабочий процесс

### Шаг 1: Уточнение параметров
Спроси недостающее: откуда/куда, **дату вылета**, число пассажиров (взрослые/дети/младенцы), предпочтения по классу обслуживания.

### Шаг 2: Поиск авиабилетов
Вызови `search_avia` с точными именами полей. Если дата не указана — НЕ вызывай поиск, сначала спроси.

### Шаг 3: Детали и оформление
- Детали оффера: `tutu_call(tool="get_offer_details", args_json='{...}')` с `view="compact"` для экономии токенов.
- Ссылка на оформление: `tutu_call(tool="create_checkout_link", args_json='{...}')`.

### Шаг 4: Итоговое предложение (Markdown)
- ✈️ Рейс (авиакомпания, время вылета/прилёта, пересадки, цена)
- 💰 Итого на всех пассажиров
- 🔗 Ссылка на оформление (если запрошено)

## Правила экономии токенов
1. В `get_offer_details` используй `view="compact"`.
2. Переиспользуй уже полученные offer_id, не дублируй поиск.
3. Не запрашивай детали, пока пользователь не выбрал конкретный рейс.

## Важные замечания
- Даты — всегда `YYYY-MM-DD`. Сегодняшняя дата есть в системном промпте.
- Не выдумывай offer_id, цены и ссылки — используй только то, что вернул `tutu_call`.

# Avia playbook (`search_avia` -> `create_checkout_link`)

## Detail card
No confirmed read-only avia detail endpoint. For a presentation card,
pass the selected compact offer object as `details_ref` to
`get_offer_details(product_type='avia', ...)` — it reformats with no
side effects.

## Flight number
The flight number is `legs[].segments[].voyage_no` (e.g. `SU-6026`) — one
per segment, so a connection shows one number per hop. Quote it verbatim;
never reconstruct a flight number from the carrier name or times.

## Filters (`direct_only`, `carriers`)
`direct_only=true` keeps only nonstop flights (every leg a single segment;
round-trip stays direct when both legs are). `carriers=[...]` keeps only offers
where every listed airline matches one of the requested names/ids; a mixed
Aeroflot+S7 offer does not satisfy "only Aeroflot".
`meta.carriers_available` is the per-route airline reference DERIVED from the
fetched offers (avia fetches the full route pool, so it's complete for the
route): each entry has `name` ("Аэрофлот"), `offers_count` and `price_from` —
plus a stable `id` ("1062") ONLY when Tutu ships its carrier facet (the current
`/avia/offers` endpoint doesn't — see the TODO-for-Tutu; filter by `name`).
Matching is a case-insensitive substring on the name, so guessing ("aeroflot"
for "Аэрофлот") silently drops everything. What
each filter removed is in `meta.post_filter_dropped_not_direct` /
`post_filter_dropped_wrong_carrier`. When a filter is active the whole route
pool is fetched before filtering, so an airline listed in `carriers_available`
reliably shows up in the filtered result and `has_more` stays honest — no thin
page from the page-scoped fetch. `meta.total_matched` is the exact count after
filters (before pagination): "сколько всего рейсов Азимута" is one search, not a
page-walk (`meta.total_matched_exact=false` only on a rare >200-offer route).

timetable — a flight absent from the current page may still operate, so
never conclude «рейса N нет» from one page while `meta.has_more` is true.

spelling of the designator works ('SU 6176', 'su6176', leading zeros),
