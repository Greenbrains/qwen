# Tutu Travel Agent v3.3 — «Долгосрочная память»

> **Версия:** 3.3 · **Дата:** 2026-08-06 · **Стек:** Python 3.13, Yandex AI Studio
> (Qwen3.6-35B-A3B через OpenAI-совместимый API), MCP-сервер tutu.ru (16 инструментов),
> SQLite (долгосрочная память), FastAPI/CLI/WebSocket.

---

## 1. TL;DR

Версия 3.3 добавляет агенту **память между сессиями** и **контроль разрастания контекста**:

1. **Долгосрочная память пользователя** в `data/memory.db` (SQLite): пользователь
   идентифицируется по алиасу + кодовому слову («Я — енот»), агент помнит его
   прошлые поиски и поднимает их в новой сессии.
2. **Компрессия истории** (`Session.compact`): старые ходы диалога схлопываются
   в маркеры `📜 [ИСТОРИЯ] …` (~50 токенов вместо ~3 500 токенов сырого JSON
   за каждый ход), сырые `role: tool` ответы MCP удаляются из контекста.
3. **Специализация специалистов**: каждый агент получает только свои инструменты
   из YAML-шапки скилла (rail → 7, avia → 4, hotels → 4, consultant → 5,
   general → все 16).
4. **Всегда свежая дата** в системном промпте через `system_prompt_provider`
   (агенты кэшируются оркестратором — раньше дата «протухала»).
5. **Настройки на pydantic-settings**, синхронизированы сигнатуры
   `PromptLoader`/`ToolRegistry`, исправлены артефакты аудита v2.x.

## 2. Ключевые изменения

### 2.1 Долгосрочная память пользователя (новое)

- Новый модуль **`client/memory.py`** → класс `MemoryStore` поверх SQLite
  (stdlib `sqlite3`, без новых зависимостей). Файл базы: **`data/memory.db`**.
- Таблицы:
  - `users(id, alias UNIQUE, passphrase_hash, created_at, last_seen)` —
    профиль пользователя; кодовое слово хранится только как SHA-256-хэш
    `sha256("alias::passphrase")`.
  - `memories(id, user_id → users.id ON DELETE CASCADE, created_at, kind,
    content, meta)` — накопленные маркеры истории (индекс по
    `user_id, created_at DESC`).
- API класса: `exists / register / verify / add_marker / get_markers /
  forget / close`.
- Политика записи: маркеры сохраняются в базу **только для идентифицированного
  пользователя** (`session.user_alias`); анонимные сессии живут только в RAM.

### 2.2 Компрессия истории (Context Compaction)

- **`client/session.py`**:
  - `Session.compact(keep_last_turns=2)` и модульная `compact_messages(...)`;
  - история разбивается на «ходы» (user → tool-обмен → финальный ответ);
    ходы старше последних двух заменяются маркером, `role: tool` удаляются;
  - из каждого усечённого ответа MCP до удаления извлекаются факты:
    число офферов, минимальная цена, маршрут, дата — маркер вида
    `📜 [ИСТОРИЯ] Запрос «поезд москва тула» | search_rail(Москва→Тула, 2026-08-06), 5 вариантов, цена от 1713 ₽ | Итог: …`;
  - схлопывание дубликатов user-сообщений подряд (фикс эффекта из логов v3.2,
    где после 500-й ошибки запрос записывался дважды);
  - плейбуки (`get_*_instructions`) в маркеры не попадают;
  - **последние 2 хода хранятся целиком** — в них живые `details_ref` /
    `checkout_ref`, необходимые для «оформи второй вариант».
- **`agents/orchestrator.py`**: `run(..., user_alias=None)` после цикла агента
  вызывает `compact_messages()` и сохраняет полученные маркеры в `MemoryStore`
  (если пользователь идентифицирован). Возвращает уже сжатую историю.

### 2.3 Специализация специалистов

- Скиллы (`agents/skills/*.md`) переписаны: список `tools` синхронизирован
  с текстом инструкций (в `rail.md` раньше не хватало `get_offer_details`,
  `create_checkout_link`, `get_etrain_instructions`), убрана «вода»,
  добавлен запрет вызывать чужие инструменты.
- **`agents/builder.py`** (`AsyncAgentBuilder`):
  - парсер понимает и классический YAML frontmatter (`--- … ---`), и плоскую
    шапку `key: value`;
  - `_resolve_tools()` фильтрует реестр по `tools` скилла + `extra_tools`
    из `AgentSpec` (consultant дополнительно получает `fetch_resource`);
  - при ошибке `tools/list` — статический fallback реестра.

### 2.4 Всегда свежая дата

- `builder.build()` передаёт в агента `system_prompt_provider` — системный
  промпт пересобирается на каждой итерации цикла (дата/«завтра»/«через неделю»
  актуальны даже в долгоживущем закэшированном агенте).
- Патч **`client/openai_agent.py`**: `OpenAIAgent`/`AsyncOpenAIAgent`
  пробрасывают `system_prompt_provider` в `BaseAgent`.

### 2.5 Подготовка к Prompt Caching

- В **`agents/prompts/prompt_loader.py`** блок «📅 ТЕКУЩАЯ ДАТА» перенесён
  в **конец** системного промпта: статичный префикс (роль + правила + скилл)
  не меняется от запроса к запросу → сервер Yandex может кэшировать префикс
  (экономия на входных токенах + быстрее TTFT).
- Синхронизирована сигнатура `PromptLoader.__init__(prompts_dir=None,
  settings=None, **kwargs)` с местами вызова (`builder.py`, `dependencies.py`).

### 2.6 Настройки и исправления аудита v2.x

- **`config/settings.py`** переписан на `pydantic-settings` (`BaseSettings`,
  `.env` читается нативно, типы валидируются); `mcp_headers` задаётся из env
  JSON-строкой; `validate_llm()` сохранён.
- Исправлены артефакты: `from __future__ import annotations`, `Path(__file__)`,
  пробелы в ключевых словах роутера (`"электричк "` → `"электричк"`),
  присвоение `_mcp` только после успешного рукопожатия, `close()` не закрывает
  чужую aiohttp-сессию и корректно закрывает AsyncOpenAI-клиент.

## 4. Пайплайн запроса в v3.3

```
Пользователь
   │  «поезд москва тула»
   ▼
CLI / FastAPI  ──► Session.history (уже сжатая + маркеры памяти)
   │
   ▼
Orchestrator._route()          1) ключевые слова → 2) LLM-роутер → 3) general
   │  выбран: rail
   ▼
AsyncAgentBuilder.build(rail)  tools = скилл rail (7 из 16)
   │                           system_prompt = база + скилл + свежая дата
   ▼
Агентный цикл (BaseAgent.run_async): LLM ⇄ MCP ⇄ LLM …
   │
   ▼
Orchestrator: compact_messages(keep_last_turns=2)
   │  старые ходы → маркеры 📜; role:tool удалены; дубли схлопнуты
   ├─► Session.messages = сжатая история
   └─► если session.user_alias: MemoryStore.add_marker(...) → data/memory.db
```

### Сценарий идентификации («Я — енот»)

1. Новая сессия → агент: *«Мы с Вами уже общались? Если да — скажите: я <имя>»*.
2. Пользователь: `я енот`.
   - алиас **не найден** → просьба задать кодовое слово → `register()`;
   - алиас **найден** → просьба назвать кодовое слово → `verify()`.
3. При успехе: `MemoryStore.get_markers("енот", 10)` → маркеры вставляются
   в начало истории → агент продолжает: *«О, енот! Мы с Вами уже искали…»*.
4. Команды CLI: `/я <имя>` — идентификация, `/память` — показать маркеры,
   `/забудь меня` — `forget()` (удаление профиля и маркеров).

> ⚠️ Алиас + кодовое слово — это **профиль, а не безопасность**
> (для продакшена — нормальный auth/токены в API-режиме).

## 5. Эффект по токенам

Фактические замеры v3.2 (логи от 2026-08-06, история накапливалась без сжатия):

| № | Запрос | Токенов за ход (∑) | Накоплено агентом |
|---|---|---:|---:|
| 1 | электричка Москва–Калуга | 10 220 | 25 367 |
| 2 | поезд Москва–Тула | 15 147 → 22 250 | 62 602 |
| 3 | самолёт Москва–Анталья | 33 459 | 86 412 |
| 4 | отели в Казани | 40 764 | 73 874 |

Причина роста: каждый ход тащил в LLM сырые JSON прошлых поисков (~12 000
символов ≈ 3 000–4 000 токенов каждый).

Ожидание в v3.3: старый ход = маркер ~50 токенов; вход 4-го запроса
снижается ориентировочно на **45–60 %**, а рост контекста перестаёт быть
линейным. Дополнительно: минус «чужие» схемы инструментов у специалистов
(avia-агент больше не возит схемы `search_rail`/`get_rail_seatmap` и т.д.).

## 8. Ограничения и следующие шаги

- [ ] Фоновая очистка `SessionStore` по TTL (сейчас — ленивая, при обращении).
- [ ] API-режим: память пока ориентирована на одну сессию/пользователя;
      для мультипользовательского REST нужен `user_id` в запросе и пер-юзерный
      системный промпт без вреда кэшированию префикса.
- [ ] Опциональный md-экспорт памяти (`/память` → файл) для отладки.
- [ ] LLM-суммаризация маркеров (сейчас — детерминированное извлечение фактов
      из JSON: быстрее и бесплатно; качество покрывает сценарий).
- [ ] Responses API: ветка в builder есть, но `AsyncResponsesAgent` пока без
      `system_prompt_provider` (дата там живёт в серверном промпте).
